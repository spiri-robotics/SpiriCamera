10.2.2. SpiriCamera.transports¶

The ways a camera’s frames leave it, each under its own topic.

A transport’s settings are ordinary synced fields, at <camera>/transport_jpeg/quality. Its frames are not: they travel at <camera>/transport_jpeg/@data, and that @ is the point. A zenoh key chunk starting with @ is verbatim: a wildcard never matches it, so the <camera>/** subscription every SpiriSynq mirror holds does not receive frames, and does not count as wanting them.

That gives a mirror a choice and the camera a signal. A mirror receives a transport’s frames only by subscribing to that exact key, and a camera none of whose transports has a subscriber isn’t running: its source is closed. The transports depend on each other in one direction:

source -> resize -> widgets -> transport_raw -> transport_jpeg
                                             -> transport_video

so anything wanting JPEG or video also wants raw, and raw is what keeps the source open. A spirisynq:// source subscribes upstream only while its own camera is running, so demand travels up a chain of relays.

A subscriber joining queries the transport’s request_keyframe key, and the camera sends its current frame again on @data, as an RTSP viewer’s PLI gets it a keyframe. A running camera sends new frames anyway, so this only matters for one whose frame isn’t changing, which isn’t republished.

This module must not import SpiriCamera.camera: SpiriCamera.sources needs these names too.

class SpiriCamera.transports.VideoSync(*, keyframes_only=False)[source]¶

Bases: object

What a video subscriber needs to know which packets it can decode.

The job an RTP stack would otherwise do. An interframe is only any use if everything back to its keyframe arrived, and the two keys can be at different priorities, so a keyframe can overtake the interframes before it:

  • Until a keyframe arrives, nothing else can be decoded.

  • An interframe from before the current keyframe is discarded.

  • An interframe that isn’t next in sequence means a gap: stop, and ask for a keyframe.

keyframes_onlybool

Whether this subscriber only takes keyframes, so the sequence numbers between them are not missing, just not for it.

class SpiriCamera.transports.TransportVideo(codec='h264', preset='veryfast', keyframe_interval=2.0, keyframe_min_interval=0.25, target_bitrate=0, encoded_fps=0.0, encoded_width=0, encoded_height=0, rate_control=<factory>)[source]¶

Bases: SubSyncableDataclass

A camera’s video transport: its one encode, whoever is watching.

Keyframes and interframes travel on separate keys so each can have its own QoS: a keyframe is the only way back after a loss, and the frames between are the first thing to shed. The QoS is SpiriSynq’s own kind: local to the sender, never synced or rehydrated, and set in code on the class or the instance as data_keyframe_qos and data_interframe_qos.

10.2.2. Attributes¶

codecstr

What is encoded. Only h264.

presetstr

libx264’s preset; defaults to SPIRICAMERA_H264_PRESET.

keyframe_intervalfloat

Seconds between keyframes, which bounds recovery from a loss. Also the frame interval of a keyframes-only subscriber. 0 sends them only when asked for.

keyframe_min_intervalfloat

Least seconds between requested keyframes, so ten joiners or one lossy link don’t cause a storm.

target_bitrateint

What the encoder is aiming at now, for the worst subscriber. A readout, set by the encoder: anything else written to it is overwritten.

encoded_fpsfloat

The frame rate being encoded now, also a readout: the camera’s max_framerate, lower only when rate control says so.

encoded_widthint

The width being encoded now, also a readout.

encoded_heightint

The height being encoded now, also a readout: the camera’s max_height is the setting, and this is lower only when rate_control.height_caps says so.

rate_controlRateControl

The policy behind those readouts.

packet_receivedSignal

Emits each VideoPacket in decodable order, in this process, which is what RTSP and other endpoints read.

class SpiriCamera.transports.DataChannel(path, receive, *, answers_keyframe_requests=True)[source]¶

Bases: object

The zenoh side of one @data key, and who wants it.

A camera wants a transport’s frames for two kinds of consumer: a subscriber somewhere on the network, which the key’s publisher can see, and something in this process, which holds the channel instead so its frames are not sent through zenoh just to come back.
