10.2.4. SpiriCamera.rtsp¶

The cameras’ RTSP server: each one’s H.264 encode and KLV metadata, over RTP.

Each camera it serves, by name, has two mounts, for the two kinds of reader:

/<name>

For a viewer across a link that needs protecting, such as QGroundControl. UDP only, because TCP hides loss. The viewer’s RTCP drives that camera’s rate control, and it can ask for lost packets again.

/<name>/relay

For a relay on the same host, such as MediaMTX, whose link has nothing to protect. TCP only, and its RTCP has no say in rate control.

What a viewer’s RTCP means to rate control is LossMeter’s job. A session holds the camera’s video while it plays, so the camera idles when nobody is watching.

SpiriCamera.rtsp.RELAY_SUFFIX = 'relay'¶

/<name>/relay.

Type:

What a camera’s mount ends in for a relay on the same host

SpiriCamera.rtsp.RTCP_SILENCE = 8.0¶

Seconds without any RTCP before a viewer’s link is taken to be down. GStreamer reports every 3 to 7.5 seconds on a clean link, so this has to be longer.

class SpiriCamera.rtsp.LossMeter(silence=8.0)[source]¶

Bases: object

Turns one viewer’s RTCP into a report to rate control every tick.

Loss comes from NACKs when there are any: they say exactly what went missing, at once, and count loss that retransmission goes on to repair, which is meant to lower the bitrate because retransmitting adds load to the link. Receiver reports are the fallback for a viewer on a clean link, or one that doesn’t NACK. A clean one vouches for all the time since the last sign of trouble, so it counts once for each second of that, as often as a SpiriSynq subscriber reports.

A viewer that has gone quiet for RTCP_SILENCE has lost everything, as far as anyone can tell. One that has never sent RTCP has no say at all.

send_datagram(payload_type, is_rtcp, data, destination)[source]¶

Send from the port a reader was told this track’s traffic comes from.

A packet the kernel has no room for is dropped, not queued: a queue on a link that can’t keep up only grows the latency, and asyncio’s own queue for a UDP transport has no limit. The reader NACKs what it missed, so a drop here counts as loss to rate control like any other.
